**Plan-review fixes (all accepted).**
1. **(P1) In-process test config.** `tests/support/invite.ts` exports `stubInviteEnv(overrides?)`, which `vi.stubEnv`s the test code's entry and generous limits; every in-process integration file calls it in `beforeAll`. The gate is injectable: `route()` uses `getGate()` by default, and a `createGatedRoute(gate)` / `createGate(...)` seam (like `createExtractPost`) lets `access-gate.test.ts` build gates with low limits and a fake clock. The composition root passes `() => Date.now()`, not `Date.now`.
2. **Fail closed covers `record` too.** The live-mode checks (codes required, committed codes refused, persistent store required, D11) apply to `live` and `record`.
3. **Both committed codes are refused** in `live`/`record`: the `.env.example` dev code and `TEST_INVITE_CODE`. AC-GATE-08 covers both.
4. **Keys and scheme.** Counters are keyed by the code's **label** (D10), which is unique and stable, never by a hash prefix. `parseBearer` matches the scheme case-insensitively (RFC 7235); a unit case covers `bearer`.
5. **The CI code reaches one step only.** The deploy workflow checks for `CONTRACT_INVITE_CODE` inside the contract step itself; AC-GATE-14 asserts exactly one step references the secret.
6. **Local limits.** `.env.example` sets limits high enough for repeated `test:contract:external` runs against `pnpm dev`, and CLAUDE.md §3 says an external target needs that.

**D10. Labelled codes, revocation that stays visible, structured logs.** (from the user's question on flagging bad actors)
- `INVITE_CODES` (renamed from `INVITE_CODE_HASHES`): comma-separated `label:hash` entries. A label is `[a-z0-9-]{1,32}` (e.g. `acme-recruiter`), not secret, and names the holder in logs and counters. The hash is the lowercase hex SHA-256 of the code. Labels are unique across both lists; a malformed or duplicate entry is a `ConfigError` in every mode.
- `REVOKED_INVITE_CODES`: the same format. A revoked code gets the same `401 UNAUTHORIZED` as an unknown one (the client learns nothing), but the server logs it as `revoked` with its label. Revoking means moving the entry from one list to the other and re-applying Terraform, so attempts after deactivation are visible.
- Every gate decision logs one JSON line: `{"event":"gate","outcome":"allowed|missing|unknown|revoked|rate_limited|quota_exhausted","code":"<label>","path":"/v1/trip/…"}` (`code` omitted when there is none). The code itself and its hash never appear. Cloud Logging can filter on these fields.
- `pnpm invite:new <label>` prints the new code and its `label:hash` entry.
- An alert on `revoked` and `quota_exhausted` events (a log-based metric) is a WU-23 Note, not this unit.

**D11. A hard lifetime cap per code, plus burst and global limits.** (replaces Q2 and D5's single window)
- **Why:** the user wants each code's total spend capped, well under $5. A count per endpoint over the code's lifetime gives a hard dollar bound: Σ (allowed requests × worst-case cost per request), where the worst case follows from each stage's `maxOutputTokens` and the ADR 0004 caps. Typical spend is a fraction of it. *Rejected:* metering actual tokens per code (only known after a call, so a call can overshoot; and it would pull usage from the use cases up into the HTTP gate).
- **Limits** (env, positive integers, else `ConfigError`). Defaults:

  | Variable | Default | Scope |
  |---|---|---|
  | `QUOTA_EXTRACT` | 60 | per code, lifetime |
  | `QUOTA_RECOMMEND` | 3 | per code, lifetime |
  | `QUOTA_PRESENT` | 5 | per code, lifetime |
  | `RATE_LIMIT_PER_HOUR` | 30 | per code, fixed hourly window |
  | `RATE_LIMIT_GLOBAL_PER_DAY` | 300 | all codes together, fixed daily window |

  Estimated worst case per code ≈ $3 (60 × ~$0.01 extract, measured from its token budget; 3 × ~$0.75 recommend, from WU-10's draft plan Q4, which charges every call at its full `maxOutputTokens`; 5 × ~$0.02 present, an estimate until WU-11). About 3 complete trip conversations per code; typical spend $0.20–0.50. The recommend quota was 5 at first approval and set to 3 once WU-10's figure was known (user decision, same day). WU-23 sets the final values from WU-10/WU-11's real worst cases. The hosted replay service, `.env.example` and the test harness set high values (replay costs nothing).
- **Responses:** the hourly and global limits → `429 RATE_LIMITED` with `Retry-After`. A spent lifetime quota → `429 QUOTA_EXHAUSTED` with **no** `Retry-After`, so a client can say "this invite has been used up". `openapi.yaml` declares both under 429.
- **`UsageStore` interface** (`src/http/usage-store.ts`): `take(counters, now)` checks every counter for a request (lifetime for the endpoint, hourly for the code, daily global) and increments **all or none**. So a request refused by one limit consumes nothing from the others, and an exhausted code can't drain the global cap with refused requests. It returns the refusing counter and its reset time (none for a lifetime counter). Async, so a database can implement it in a transaction.
- **WU-22 ships `MemoryUsageStore` only.** Counts reset on every restart (Cloud Run scales to zero), so it is not a hard cap. Hence a new fail-closed rule: `live`/`record` with `USAGE_STORE=memory` (the only value WU-22 accepts) is a `ConfigError`. Live mode therefore can't start until WU-23 adds a persistent store. Replay costs nothing, so the hosted replay service is unaffected.
- Accepted: a request that passes the gate but then fails 413/422/502 still consumes its counts.
- **Held for the close commit (WU-23 Note, plus a Definition-of-done change for explicit approval then):** WU-23 adds a Firestore `UsageStore` (free tier; Terraform for the database and the runtime account's `datastore.user` role) and sets the final limits from WU-10/WU-11's worst cases. DoD: "the live service runs with a persistent usage store; `live` refuses to start without one." Also: drop or tightly cap the CI code on the live service (D9), and add an alert on `revoked`/`quota_exhausted` (D10).

## 1. Goal & scope

**Goal** (from `docs/work-breakdown.md`): only people given an invite code can use the trip endpoints, and each code has a rate limit. This is the access control [ADR 0005 §5](../decisions/0005-hosting-and-access.md) chooses instead of user accounts. It lands before WU-12, so the web client and its pact include it from the start.

**In scope**
- `docs/features/access-gate.md` with `AC-GATE-xx` criteria.
- **Contract (breaking):** the three trip endpoints require `Authorization: Bearer <invite code>`, declared as an HTTP bearer security scheme in `openapi.yaml`. A missing or unknown code → `401 UNAUTHORIZED`; over the limit → `429 RATE_LIMITED` with `Retry-After`. `GET /v1/health` and every CORS preflight stay open, and preflights allow the `Authorization` header. `contractVersion` 0.5.0 → 0.6.0. CLAUDE.md §5 (endpoint table, status codes, CORS).
- **api-nextjs:** code hashes from an env var, matched in constant time, never logged; fail closed in `LLM_MODE=live`; an in-memory per-code fixed-window rate limiter with an injected clock; limits as config.
- `.env.example` and the test harness supply codes. A small `pnpm invite:new` script makes a code and its hash.
- **Conformance:** 401 without a code and with an unknown one, on every trip endpoint; health and preflight open without one; preflight allows `Authorization`. All existing checks send the code, read from `CONTRACT_INVITE_CODE`.
- **Post-deploy check (the WU-21 open question):** a CI-only invite code, decided and recorded in an ADR 0005 addendum (D9), wired into `deploy.yml` and `infra/service.tf`.

**Out of scope**
- The web client's header, invite link (`?invite=`) and 401/429 UI: WU-12 and WU-13. The ADR addendum covers the URL-logging tradeoff, as the Notes ask.
- Setting the live limits from measured cost, Secret Manager for the hashes, and removing the CI code from a live service: WU-23.
- Per-IP limits on failed attempts (D5 explains why not), user accounts, a shared-store limiter (ADR 0005 "If this became a product").
- Re-recording cassettes: the header never reaches the model request, so cassette keys don't change.

## 2. Approach & key decisions

**D1. Contract shape.** ([CLAUDE.md §5](../../CLAUDE.md#5-http-api-v1), §10)
- `components.securitySchemes.inviteCode = { type: http, scheme: bearer }`. Each trip POST declares `security: [{ inviteCode: [] }]`; `/v1/health` declares `security: []`. No top-level `security`, so an operation is open only where it says so in the generator, and a gen test pins which.
- Two new `ErrorCode` values: `UNAUTHORIZED` (missing, malformed or unknown: one code, so the response never says which) and `RATE_LIMITED`.
- New response components `Unauthorized` (with a `WWW-Authenticate` header, value `Bearer`, as RFC 6750 requires on a 401) and `RateLimited` (with a required `Retry-After` header: an integer number of seconds ≥ 1). Both use the `ErrorResponse` body, which carries CORS like every other response.
- A breaking change: `feat(domain-schema)!` with a `BREAKING CHANGE:` footer and `contractVersion` 0.6.0 (pre-1.0, so a breaking change bumps the minor, as 0.4.0 and 0.5.0 did). **This commit stands alone** (required by the unit's Notes and §10).
- *Rejected:* a custom `X-Invite-Code` header (non-standard; `Authorization` is what HTTP clients, Pact and OpenAPI tooling understand); separate codes for missing vs unknown (tells a prober nothing useful, but there is no reason to distinguish).

**D2. Check order, and where the gate lives.** The gate runs inside the existing `route()` wrapper, before the body is read: **401 → 429 → 413 → 422 → handler**. So an unauthenticated caller can't make the server read a megabyte, and 401/429 get CORS and the error envelope for free. `route()` becomes gated **by default**; the one open route uses an explicit `openRoute()` (health). `preflight` stays open. So a new route that uses the normal wrapper is gated without anyone remembering to ask (DoD), and an integration test enumerates every `route.ts` and proves it (AC-GATE-10). Every authenticated request to a trip endpoint counts toward the limit, including ones that then fail with 413 or 422.
- *Rejected:* Next middleware (couples the gate to `next/*`, which §9 keeps out of `src/` logic, and runs outside our error envelope); a per-handler check (a new route could forget it).

**D3. Codes are stored as hashes, matched in constant time.** ([ADR 0005 §5](../decisions/0005-hosting-and-access.md): "the server stores only each code's hash")
- `INVITE_CODE_HASHES`: a comma-separated list of lowercase hex SHA-256 digests of the codes. A code is 32 random bytes in base64url (`pnpm invite:new`), so a fast hash is enough: there is nothing to brute-force, and a leaked hash can't be used as a bearer.
- Matching: hash the presented code, then compare its digest with **every** stored digest using `crypto.timingSafeEqual`, without exiting early. Digests have a fixed length, so neither the code's length nor which entry matched shows in the timing.
- **Never logged:** the code itself appears in no log line. A request that passes logs `[gate] code=<first 8 hex of its hash>`; a 429 logs the same id; a 401 logs only `reason=missing|unknown`. That id is how usage is visible per code. Config errors name the variable, never the value (as `ConfigError` already does).
- *Rejected:* plaintext codes in the env var (the ADR says hashes); bcrypt/scrypt (slow hashing protects low-entropy passwords; these codes are random 256-bit values).

**D4. Fail closed; config lives in its own loader.** `loadAccessConfig(env, llmMode)` in `src/http/access-config.ts`, memoized like `getConfig()` and called from `instrumentation.ts` at startup:
- `LLM_MODE=live` without `INVITE_CODE_HASHES` → `ConfigError` → the server exits (the existing `register()` path).
- `live` with the **local dev code's hash** (the one committed in `.env.example`) → `ConfigError`: a committed code must never open a live service.
- Any malformed entry (not 64 hex chars) → `ConfigError`, in every mode.
- `replay` / `mock` / `record` with no hashes → starts, logs one warning, and every trip request is a 401. Still closed, just useless.
- A separate loader, not a field of `loadConfig`, because `eval/run.ts` calls `loadConfig({ LLM_MODE: 'live' })` in-process and serves no HTTP; it must not need invite codes. The module stays free of Node APIs (only regex checks; the dev hash is a literal), because `instrumentation.ts` is also compiled for Edge.

**D5. Rate limiter: fixed window per code, injected clock.** (CLAUDE.md §6.1; ADR 0005 §4)
- `createRateLimiter({ maxRequests, windowMs, now })` → `take(codeId)` returns `{ allowed: true }` or `{ allowed: false, retryAfterSeconds }` (`ceil` of the time left in the window, at least 1). Each code's window starts at its first request and resets lazily. Production passes `Date.now` at the composition root; tests pass a fake clock.
- `RATE_LIMIT_MAX_REQUESTS` (default 60) and `RATE_LIMIT_WINDOW_SECONDS` (default 3600), positive integers, else `ConfigError`. WU-23 sets the live values from measured cost. Q2 asks about the defaults.
- Memory is bounded by the number of configured codes, because unknown codes are rejected before the limiter. In-memory is correct only because `max instances = 1` (ADR 0005 §4); a comment and the ADR addendum say so.
- **No limit on failed attempts.** Guessing a 256-bit code is hopeless, and per-IP limits behind Cloud Run's front end would need `X-Forwarded-For` trust rules for no real gain.
- *Rejected:* a sliding window or token bucket (smoother, but a fixed window is simpler to reason about and to test; the burst at a window boundary is at most 2× the limit, which the Anthropic spend limit bounds anyway).

**D6. CORS.** The preflight allows `content-type, authorization`. Every response also sends `Access-Control-Expose-Headers: Retry-After`, because `Retry-After` isn't a CORS-safelisted response header, so a browser client couldn't otherwise read it on a 429. `WWW-Authenticate` doesn't need exposing; the client branches on the error code.

**D7. Test harness codes.**
- `backends/api-nextjs/tests/support/invite.ts`: a fixed `TEST_INVITE_CODE` and its hash, and an `authHeaders()` helper. `baseEnv()` in `api-server.ts` sets `INVITE_CODE_HASHES` and generous `RATE_LIMIT_*` values, so a developer's `.env.local` can't change a test (same reason as the other variables there).
- `scripts/run-contract.ts`: when it starts its own server, it **makes a fresh random code per run**, gives the server its hash and the suite the code (`CONTRACT_INVITE_CODE`). With `--external`, `CONTRACT_INVITE_CODE` is required, like `API_BASE_URL` (`plan-run.ts`).
- `scripts/test-image.ts`: the same per-run code, passed to the container as `INVITE_CODE_HASHES` and to the suite.
- `.env.example`: `INVITE_CODE_HASHES` set to the hash of a documented local dev code (`local-dev-invite`), which the web client (WU-12) will send in `pnpm dev`, plus the `RATE_LIMIT_*` variables, and `CONTRACT_INVITE_CODE` under tests.
- `pnpm invite:new` (`scripts/invite-code.ts`): prints a new random code and its hash, reusing the backend's `hashInviteCode`. Taking no argument keeps codes out of shell history.

**D8. Conformance suite (black-box, §6.5).**
- `support/http.ts`: every request helper sends `Authorization: Bearer <CONTRACT_INVITE_CODE>` by default, with an option to send none or a given value. `support/artifacts.ts` gets `inviteCode()`, which throws a clear error when the variable is unset.
- New `conformance/access.test.ts` + `checks/access.ts`: for each trip endpoint, with a schema-valid body: no header → 401 `ErrorResponse` `UNAUTHORIZED` with `WWW-Authenticate` naming `Bearer` and the allow-origin header; a random unknown code → the same; `GET /v1/health` with no header → 200. The preflight check (`cors.ts`) also requires `authorization` in `Access-Control-Allow-Headers` (or `*`).
- No black-box 429 check: the limits are deployment config, and hammering a live backend until it says 429 would cost money once WU-23 goes live. 429 is proven at the integration layer.
- `self-test/fake-backend.ts` gates like a conformant backend, and the self-test adds broken fakes: one that doesn't gate, one that gates health, one whose preflight omits `authorization`. Each must fail its check (AC-CONTRACT-09 pattern).
- `pact-verify.test.ts` passes `customProviderHeaders: ['Authorization: Bearer <code>']`, so WU-12's pact, which will carry an example code, verifies against any backend with the real one. The wiring pact (health) is unaffected.

**D9. The post-deploy contract check gets a CI-only code.** (the unit's open question; recorded in an ADR 0005 addendum)
- A dedicated code for CI. Its hash goes in the hosted service's `INVITE_CODE_HASHES` (a Terraform variable `invite_code_hashes`, set in the git-ignored `terraform.tfvars`); the code is a fourth Actions secret, `CONTRACT_INVITE_CODE`, passed only to the "Provider contract tests" step. In replay mode it can spend nothing.
- `infra/service.tf` also sets `RATE_LIMIT_MAX_REQUESTS` / `RATE_LIMIT_WINDOW_SECONDS` high enough that back-to-back deploys can't trip the limit (one contract run is ~60 requests; proposed 1000 per hour in replay).
- **For WU-23:** once live, this code would spend real money on every deploy. WU-23 either drops its hash from the live service or keeps it with a low limit; a Note says so.
- *Rejected:* a manual post-deploy step (loses the automatic proof WU-21 built); skipping the gated checks after deploy (then the hosted gate is never proven).
- The addendum also records: hashes only (D3); the in-memory limiter's one-instance assumption (D5); revocation = remove the hash and re-apply Terraform; and that an invite link (`?invite=<code>`, WU-13) can end up in logs and browser history, which this threat model accepts (a code is revocable, rate-limited, and bounded by the spend limit).
- **Rollout order** (by hand, before the merge; R1): generate the CI code, add its hash to `terraform.tfvars`, `terraform apply` (the old image ignores the new variables), set the `CONTRACT_INVITE_CODE` secret. The first deploy from `main` then proves it. I'll give you the exact commands; I won't apply Terraform or set secrets without your say-so.

## 6. Risks & open questions

**Risks**
- **R1. Deploy order.** If the PR merges before the hosted service has the CI code's hash and the secret exists, the post-deploy check fails on 401s (the service itself is fine; it just rejects everything). Mitigation: the D9 rollout before the merge; the runbook covers it; a failure is fixed forward by applying Terraform and re-running the workflow.
- **R2. Every existing HTTP test needs the header.** A missed one fails loudly with a 401, so the risk is churn, not silent gaps.
- **R3. A local `.env.local` without `INVITE_CODE_HASHES`** makes `pnpm dev` answer 401 to everything. Mitigated by the startup warning and `.env.example`. WU-12 is the first real consumer.
- **R4. Pact `customProviderHeaders`** replaces the header for every interaction. If WU-12 ever needs a pact interaction *without* the code (a 401 interaction), it will need a request filter instead. Noted for WU-12.

**Open questions (recommended answer first)**
- **Q1. Error code names:** `UNAUTHORIZED` and `RATE_LIMITED` (recommended; mirror the status), or `INVALID_INVITE_CODE` and `RATE_LIMITED`.
- **Q2. Default limits:** 60 requests per hour per code (recommended; a demo conversation is maybe 10–20 requests), with the hosted replay service at 1000/hour. WU-23 sets live values regardless.
- **Q3. Post-deploy code (D9):** a CI-only code as a fourth Actions secret (recommended), or a manual post-deploy step.
- **Q4. Rollout (D9):** I prepare the commands and you run `terraform apply` and `gh secret set` (recommended), or I run them via PowerShell after you approve each one.
- **Q5. Prove the deploy on a scratch branch first** (as WU-21 did)? Recommended **no**: the deploy workflow change is one env line on one step; the merge's own deploy proves it, and R1's fix-forward is cheap.
