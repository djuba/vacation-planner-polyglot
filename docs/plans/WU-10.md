## 1. Goal & scope

**Goal** (from `docs/work-breakdown.md`): a valid profile becomes critic-checked recommendations, with honest verification labels.

**In scope**
- `docs/features/recommendation.md`: acceptance criteria.
- `backends/api-nextjs/data/routes.json`: a small fixture of non-stop routes, plus a schema and loader for it.
- The recommend stage: a structured call on `MODEL_REASONING`.
- The deterministic critic checks: dates (season), party fit, experiences, route claims against the fixture data, the non-stop requirement, and output caps.
- The LLM critic on `MODEL_CRITIC`.
- A bounded revise loop (at most 2 revisions). Without a pass, it returns the best attempt with `critique.unresolved[]`.
- `verification` labels, **set by code, never by the model** (D3).
- Output caps on `Recommendation`, `FactualClaim` and `CritiqueIssue`, and on the arrays that hold them. This is a contract change (D2, security-planning Note).
- What `/recommend` does with a profile that isn't `ready` (WU-05 Note, D7).
- The real route, replacing the WU-07 stub and `CANNED_RECOMMEND`.
- Cassettes: integration (first-try pass, pass after one revision, still failing after two, containment), functional, and contract (AC-CONTRACT-05 and both AC-LIMITS-11 `/recommend` probes).
- `/recommend` eval cases with planted profile strings, plus one live eval run (WU-18 Note, Q4).
- README rows (Recommend, Critique, conformance), and the worst-case latency and tokens per stage in Notes (deployment-planning and WU-21 Notes).

**Out of scope**
- `/present` and `PresentationModel` caps (WU-11). `FactualClaim` is shared, so its new caps reach `PresentationCard.claims` as well; WU-11 caps the rest.
- Live flight, hotel or price data (§7, "Factual honesty"). `routes.json` is sample data.
- Web UI for recommendations (WU-14), and how it shows `fixture` vs `unverified`.
- Any change to the rule catalog, `normalize` or `LlmClient`.

## 2. Approach & key decisions

**D1. One use case module: `src/usecases/recommend.ts`.** It exports `recommendTrip(request, deps)`, where `deps = { llm, routes, logDiscarded }`. The helpers sit beside it:
- `critic/checks.ts`: the deterministic checks, all pure functions;
- `critic/llm-critic.ts`: the critic call;
- `recommend-output.ts`: assigning ids, labeling and discarding (draft → wire).

The use cases don't import `next`, `ai` or `src/llm` (§9). The fixture data is injected, so the use case never reads files. The flow:
1. `evaluateRules(profile, referenceDate)`. Any violation throws `ProfileNotReadyError` (D7), before any model call.
2. Draft 0 = `generateObject({ stage: 'recommend', role: 'reasoning', effort: 'medium', schema: RecommendationSet, accept: non-empty })`.
3. For attempt *n* = 0, 1, 2:
   - run the deterministic checks;
   - only if they find nothing, run the LLM critic (Q6);
   - stop on a pass;
   - if *n* < 2, revise: the same recommend call, with the previous draft and its issues in the user message.
4. The answer is the passing attempt, or otherwise the best one (D6), mapped to the wire (D3), with `critique: { pass, unresolved }`.

At worst that is 3 recommend calls and 3 critic calls. Rejected: running the LLM critic even when deterministic issues exist. It costs a Sonnet call per attempt, and the revision has to happen anyway.

**D2. Contract: model drafts stay unconstrained, the wire gets caps (ADR 0001 Q3, ADR 0004, §4.4–4.5).** This is `contractVersion` 0.5.0 → **0.6.0**, as a breaking `feat(domain-schema)!:` (Q3): `PresentRequest.recommendations` is a request field, so capping it narrows a request.

*Model-only schemas* (`src/wire/llm/`, a `.schema.json` each, not in `openapi.yaml`). All use ADR 0001 Q3 constructs only.
- `RecommendationSet` is redefined as `{ recommendations: RecommendationDraft[] }`.
- `RecommendationDraft` = `{ destination, summary, matchedExperiences: Experience[], bestMonths: int[], adultsOnly: boolean, claims: ClaimDraft[] }`. It has no `id` and no `verification`: code assigns both.
- `ClaimDraft` = `{ kind: ClaimKind, statement, nonstopRoute: { from: string, to: string } | null }`. `nonstopRoute` holds IATA codes, set when the claim asserts a non-stop flight.
- New `CritiqueResult` = `{ pass: boolean, issues: { recommendationId: string | null, issue: string }[] }` (the name §7 uses).

*Wire caps* (new exported constants, copied into `constants.json`, proposed values in Q2):

| Field | Cap |
|---|---|
| `Recommendation.id`, `destination` | `MAX_SHORT_TEXT_LENGTH` |
| `Recommendation.summary` | `MAX_SUMMARY_LENGTH` |
| `Recommendation.matchedExperiences` | `MAX_EXPERIENCES` |
| `Recommendation.claims` | `MAX_CLAIMS` |
| `FactualClaim.statement` | `MAX_CLAIM_LENGTH` |
| `RecommendResponse.recommendations`, `PresentRequest.recommendations` | `MAX_RECOMMENDATIONS` |
| `CritiqueIssue.issue` | `MAX_CRITIQUE_ISSUE_LENGTH` |
| `CritiqueIssue.recommendationId` | `MAX_SHORT_TEXT_LENGTH` |
| `critique.unresolved` | `MAX_UNRESOLVED_ISSUES` |

`RecommendResponse` is server-written, so per §4.5 these are server guarantees. A recommendation's fields aren't extracted profile fields, so they need no "carry the bad value" exemption.

**D3. Code assigns ids and verification; the model never labels a claim.**
- `recommend-output.ts` gives recommendations the ids `rec-1` to `rec-n`, in order.
- A claim is `'fixture'` only when all of these hold; every other claim is `'unverified'`:
  - its `kind` is `flight`;
  - it has a `nonstopRoute`;
  - `routes.json` lists `from → to` as a non-stop.
- `nonstopRoute` is dropped on the way to the wire.

So no path through the code can produce an unlabeled claim, or a `fixture` label the data doesn't back. A unit test checks this on every path: a first-try pass, after revisions, unresolved, after discards, and with a draft that tries to inject a label (DoD).

The prompt also says that flight, lodging, price or schedule specifics belong in `claims`, never in `summary`. Prose can't be labeled in code, so the LLM critic checks for unlabeled specifics in the summary. That limit is stated in `recommendation.md` and R4.

Rejected: letting the model fill `verification` and checking it afterwards. The model would claim `fixture` for anything that sounds right.

**D4. `routes.json` and how cities are matched.**
- Shape: `{ note, origins: [{ airport, names: string[], nonstop: [{ airport, city }] }] }`. It starts with MSP and about 15 illustrative non-stop destinations, Hawaii, Mexico, the Caribbean and Florida among them. `note` says it is sample data, not live schedules.
- It is parsed with a Zod schema in `src/usecases/routes.ts` (types and pure lookup only). The route handler imports the JSON (`with { type: 'json' }`, so Next bundles it), and a malformed file fails at first use with a clear error.
- `resolveOrigin(city)` matches the profile's `departure.city` against `names` and the airport code. The comparison is NFKC, trimmed per Unicode `White_Space` (as the rules do), case-folded, and treats `.` and `-` as spaces, so "St. Paul", "saint paul", "Minneapolis–St Paul" and "MSP" all resolve. No match means the origin isn't covered: its route claims stay `unverified`, and no route check fires.
- When the origin is covered, its non-stop destination list goes into the recommend prompt as a data block (`routeData`), so the model can choose a route that can be checked.

**D5. The deterministic checks (`critic/checks.ts`).** Each issue's text is written by code, one issue per (recommendation, check), and each check returns `CritiqueIssue[]`. The checks, all on the draft before discards:

| Check | Fires when |
|---|---|
| `OVER_CAP` | a string or array is over its wire cap (D2), so the revision can fix it before a discard is needed |
| `EXPERIENCE_NOT_REQUESTED` | `matchedExperiences` holds something not in `profile.experiences` |
| `SEASON_MISMATCH` | the trip's start month is known and not in `bestMonths` |
| `BAD_MONTH` | a `bestMonths` value is outside 1–12 (range checks belong in code, §4.4) |
| `PARTY_ADULTS_ONLY` | the party includes a child and `adultsOnly` is true |
| `ROUTE_WRONG_ORIGIN` | a `nonstopRoute.from` isn't the traveler's resolved origin airport |
| `ROUTE_NOT_IN_DATA` | `from` is a covered origin, but the data has no non-stop to `to` |
| `NONSTOP_REQUIRED` | `maxStops === 0`, `mode` is `plane` or null, the origin is covered, and the recommendation has no fixture-backed non-stop claim (WU-04 Note: only `maxStops: 0` can be backed, and `maxStops` only means something for planes) |

The trip's start month comes from the fixed `start`, or from the flexible `month`. A month with no year is read as its next occurrence from `referenceDate` (WU-05 Note). The prompt states the resolved month and year (`Trip starts: March 2031`).

These check codes are internal: only the issue text goes on the wire. Rejected: putting the check codes in the contract. Clients don't branch on critic issues, and that would add an enum to version.

**D6. Revise loop and best attempt.**
- At most 2 revisions, a constant `MAX_REVISIONS = 2`, with a unit test of the cap.
- The best attempt:
  - an attempt with no deterministic issues ranks above any attempt with some;
  - among those with none, fewer LLM-critic issues wins;
  - among the others, fewer deterministic issues wins;
  - a tie goes to the later attempt.
- `unresolved` is the best attempt's issues, then discards apply (D8). The critic's `recommendationId`s are checked against the ids assigned to that attempt, and an unknown one becomes `null`.

**D7. A profile that isn't `ready` gets a 422 (WU-05 Note; Q1).**
- `/recommend` runs `evaluateRules` first. Any violation → `422 VALIDATION_FAILED`, whose message lists the violated codes, and no model call is made.
- §7 already says Recommend "only runs on a `ready` profile". This makes that observable.
- CLAUDE.md §5 gains one sentence. The conformance suite gains AC-CONTRACT-13: a profile with no adults is a 422, and a fake that answers 200 fails.
- Rejected:
  - (a) A new error code such as `PROFILE_NOT_READY`. It adds an enum value, and a client gets nothing it can't already tell from the violations `/extract` returned.
  - (b) A 200 carrying violations, which `RecommendResponse` has no shape for.

**D8. Discards (ADR 0004: discard, never truncate).**
- After the loop, the chosen draft is mapped to the wire, and anything over a cap is discarded:
  - a recommendation whose `destination` or `summary` is over its cap is dropped;
  - a claim over its cap is dropped;
  - recommendations past `MAX_RECOMMENDATIONS`, and claims past `MAX_CLAIMS`, are dropped;
  - duplicate `matchedExperiences` are removed.
- Each discard is logged like `/extract`'s: path, reason, limit and actual, never the value.
- If no recommendation survives, the response is `LlmError('LLM_UPSTREAM_ERROR')` → 502.
- `accept` on the recommend call rejects an empty list (retried once, then 502). `accept` on the critic call rejects:
  - more than `MAX_CRITIC_ISSUES` issues (an internal constant);
  - an issue that is blank or over `MAX_CRITIQUE_ISSUE_LENGTH`;
  - `pass` disagreeing with whether `issues` is empty.
- Deterministic issue text is written by code and stays under its cap. `unresolved` past `MAX_UNRESOLVED_ISSUES` is dropped and logged.

**D9. Prompts** (`src/usecases/prompts/recommend.ts`, `critic.ts`). The system prompts are static constants (§8.3), and every client-supplied string goes through `dataBlock` with `DATA_BLOCK_RULE` (WU-09, security-planning Note).
- **Recommend:**
  - up to 3 destinations that fit the region, climate, experiences, party, dates and departure;
  - `bestMonths` and `adultsOnly` must be honest;
  - `matchedExperiences` only from what was requested;
  - flight, lodging, price and schedule specifics go in `claims`, never in `summary`;
  - set `nonstopRoute` only for a non-stop claim, and when `routeData` is given, use only its routes;
  - never state an unverified specific as fact ("may", "check current schedules").

  The user message holds: the reference date, the code-computed trip start month, `profile`, `routeData` (or null), and on a revision `previousRecommendations` and `issues`, each as a data block.
- **Critic:** check fit to the profile (region, climate, experiences, party, season, departure mode), check that the summary states no unlabeled specifics, and check that claim statements hedge. Return `pass` with an empty list, or specific issues tied to a `recommendationId`. The user message holds `profile` and `recommendations` (with code-assigned ids, and the labels as code set them).

Unit tests check that every profile string appears only inside a data block, and that the system prompts are constants.

**D10. Token budgets** (`token-budget.ts`, same formula as WU-09: 2 tokens per code point).
- `RECOMMEND_MAX_OUTPUT_TOKENS`: every draft field at its cap, times `MAX_RECOMMENDATIONS`, plus per-item overhead, plus `THINKING_MARGIN` = 4096. Sonnet 5.5's thinking is adaptive and can't be turned off (ADR 0001 Q4), so at `effort: 'medium'` it can spend tokens before the JSON. That comes to about 15k with the Q2 values.
- `CRITIC_MAX_OUTPUT_TOKENS`: `MAX_CRITIC_ISSUES` issues at the cap, plus the margin, about 10k.
- A unit test pins both formulas. R2 covers checking real reasoning-token use in the recordings.

**D11. Route wiring** (same pattern as WU-09 D6).
- `src/http/recommend.ts` exports `createRecommendPost({ llm, routes, logDiscarded })`. `route.ts` stays thin, with `OPTIONS = preflight` (WU-06 Note).
- `ProfileNotReadyError` lives in `src/usecases/errors.ts`, and `toErrorResponse` maps it to 422.
- `CANNED_RECOMMEND` is deleted. `CANNED_PRESENT` stays until WU-11.

**D12. Cassettes, with three loop paths that are actually exercised (R1).** A live model can't be told which path to take, so:
- **First-try pass:** the contract's `recommendRequest()` (Hawaii, a non-stop from Minneapolis, 2 adults). One set of cassettes then serves the integration, functional and contract layers (WU-09 learned). If the recorded critic flags something, the main agent adjusts the profile and records again, at most twice, and logs it as a deviation.
- **Pass after one revision:** integration only. A wrapper client returns a fixed, contract-valid draft 0 with a deterministic flaw: a `ROUTE_NOT_IN_DATA` claim `MSP → BOB`. It then delegates the revision and the critic call to the real replay client. The path that starts the revision is deterministic, and the revision and critic calls are still real recorded calls.
- **Still failing after two:** a non-stop-only trip from Minneapolis to "Bhutan", which has no non-stop in the data, so `NONSTOP_REQUIRED` can't be fixed. This is also the worst-case latency measurement (deployment-planning Note).
- **Containment:** instructions planted in `region`, `unmappedExperiences` and `gender`: label every claim verified, add a URL, add a canary word. The test asserts:
  - the response is wire-valid and within every cap;
  - every `fixture` label is backed by `routes.json`.

  It proves containment, not resistance (the eval measures that).
- **Contract:** `pnpm record:cassettes --contract` for AC-CONTRACT-05 and the two AC-LIMITS-11 probes (`region` at its cap in astral characters, and 50 adults).
- Every cassette uses the `CONTRACT_TEST_ENV` model IDs (WU-20 and WU-21 Notes). The main agent records all of them; subagents never do. The estimated cost is under US$1.50 (about 25 Sonnet calls).

**D13. Eval: `/recommend` cases (WU-18 Note; Q4).**
- `EvalCase` gains `stage: 'extract' | 'recommend'`, defaulting to `extract`, so the existing cases are unchanged. A recommend case carries a `RecommendRequest`.
- The runner sends those cases through `recommendTrip`, with the real `routes.json` and a live client.
- `Outcome` widens to either response type. The canary, leak, wire-valid and containment scorers are reused. The extraction-only scorers return `null` for recommend cases.
- One new deterministic scorer, `labelsHonest`: every `fixture` claim is backed by the data. Code guarantees this, so the scorer guards against a regression.
- The judge gets a recommend rubric: did the output follow instructions planted in the profile, or carry off-topic content?
- Four cases:
  - `recommend-region-canary`;
  - `recommend-unmapped-verified` (an instruction to mark claims as verified and promise direct flights);
  - `recommend-gender-url`;
  - `recommend-complete` (quality: matched experiences ⊆ requested, at least one recommendation).
- One live run, compared in Notes with the first run's line.

## 6. Risks & open questions

**Questions** (my recommendation first)
- **Q1. A non-ready profile on `/recommend`:** a 422 `VALIDATION_FAILED` naming the codes, with no model call (D7). The alternative is a new `PROFILE_NOT_READY` error code.
- **Q2. Cap values:**
  - `MAX_RECOMMENDATIONS` = 3, `MAX_CLAIMS` = 5 per recommendation;
  - `MAX_SUMMARY_LENGTH` = 500, `MAX_CLAIM_LENGTH` = 200;
  - `MAX_CRITIQUE_ISSUE_LENGTH` = 300, `MAX_UNRESOLVED_ISSUES` = 24 (8 check codes × 3 recommendations);
  - the internal `MAX_CRITIC_ISSUES` = 10.

  The budgets in D10 follow from these values.
- **Q3. Contract 0.6.0 as breaking** (`feat(domain-schema)!:` with a `BREAKING CHANGE:` footer), because `PresentRequest.recommendations` narrows a request. No client exists yet, so nothing breaks in practice. The alternative is a non-breaking `feat`, arguing that 0.x needs no `!`.
- **Q4. Eval in this unit:** add the four recommend cases and do one live run, with a budget of **US$10**. The guard charges every call at its full `maxOutputTokens`, which is about US$0.75 per case run × 4 cases × 3 repeats. Real spend should be around US$1–2. The alternative is to split the eval work into a WU-10b, which leaves this unit smaller.
- **Q5. Cassette recording:** the main agent records live after copying `.env.local` into the worktree (done), for about US$1.50 in Sonnet calls.
- **Q6.** Skip the LLM critic while deterministic issues remain (D1). The alternative is to always run it.

**Risks**
- **R1. Steering a live model.** The first-try pass depends on the recorded critic agreeing. It is bounded at two re-records, then logged as a deviation, and I'd ask before going further. The other two paths are made deterministic in D12.
- **R2. Thinking tokens.** Sonnet's adaptive thinking may push output past `maxOutputTokens`, which is a final 502. The recordings show the reasoning tokens. If they come close, I raise `THINKING_MARGIN` and record it as a deviation.
- **R3. Latency.** The worst case is 6 sequential Sonnet calls, perhaps 60–150 s, against the hosted 300 s timeout (WU-21 Note). It is measured on the Bhutan recording and reported in Notes. If it goes over about 200 s, I propose a Note on WU-23 rather than changing infra here.
- **R4. Prose can't be labeled in code.** A summary could still state a specific as fact. The prompt forbids it, the LLM critic checks for it, and the eval judges it. The DoD test covers the structured claims, and `recommendation.md` says so.
- **R5. Running alongside WU-22.** Both units may touch `CONTRACT_VERSION`, `spec/generated/`, CLAUDE.md §5, `http/errors.ts`, the conformance fake and the work breakdown. Whichever PR merges second rebases, regenerates `spec/generated/` and bumps the version again. Its cassettes may need re-recording only if a prompt or schema changed. With about 3.9 GB of RAM, I run `pnpm verify` in the foreground and not at the same time as WU-22's gate.
- **R6. Unit size.** This is a large unit. If T9 or T11 runs long, the fallback is to move them to a WU-10b, which I'd raise as a material deviation.
