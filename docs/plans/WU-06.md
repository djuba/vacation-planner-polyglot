# WU-06 — `api-nextjs` skeleton: plan

**Status:** approved (2026-11-05) with the revisions in §9, which override the sections above · **Depends on:** WU-04 (done) · **Author:** main agent (Opus), 2026-11-05

## 1. Goal & scope

**Goal** (from `docs/work-breakdown.md`): a running, decoupled API service with the HTTP plumbing and the functional-test harness in place, and no AI yet.

**In scope**
- Next.js app on :4000, Route Handlers only, no pages. `GET /v1/health`.
- Shared handler adapter: wire-schema parse → 422 envelope; error mapping → 500/502 envelopes.
- CORS for `WEB_ORIGIN`, including the preflight for a JSON `POST` (ADR 0001, Q7).
- Request body size cap at the HTTP layer (WU-04 A8).
- Config module reading env (model IDs, `LLM_MODE`, origin), validated at startup.
- Functional harness: build, start on a random port, wait for health, tear down, clean on Windows.
- `docs/features/api-skeleton.md` with ACs (§6.2). Not listed in the unit's scope, but §6.2 requires it for every feature.
- Proving WU-04 R1: Next compiles the contract's `.ts`-extension imports through `transpilePackages`.
- Root `pnpm dev` (§3 table), which runs only the API until WU-12.

**Out of scope**
- Trip endpoints, including stubs (WU-07 adds them; WU-09–11 implement them).
- `LlmClient`, `src/llm/`, cassettes (WU-08). Config only *validates* `LLM_MODE` and model IDs; nothing consumes them yet.
- `tests/contract` and the `test:contract` stub (WU-07).
- Any wire schema change, `gen` output change or `CONTRACT_VERSION` bump. If one turns out to be needed, that is a material deviation and I stop and ask.
- JSON bodies for framework 404/405 (see Q3).

## 2. Approach & key decisions

| # | Decision | Why / CLAUDE.md | Rejected alternative |
|---|---|---|---|
| D1 | **Four small modules under `src/http/`:** `cors.ts`, `body.ts`, `errors.ts`, `route.ts`. None imports `next/*`; they use only standard `Request`/`Response`. | §9: thin route handlers, portable logic, lint-enforced. | A single `adapter.ts` (god module); `NextRequest`/`NextResponse` (couples logic to Next). |
| D2 | **Adapter API.** `route(handler)` wraps `(Request) => Response \| Promise<Response>`: it catches every throw into the envelope and adds CORS to every response. `postRoute(schema, handler)` = `route` + `parseJsonBody`; the handler gets the typed body. `jsonResponse(schema, value, status?)` `safeParse`s the *outgoing* value and throws on mismatch, so a contract-breaking response becomes a logged 500. `preflight` is the shared `OPTIONS` export. Handlers return a `Response`, so WU-11's stream goes through the same wrapper unbuffered (CORS is added by rebuilding the `Response` around the same body stream). | §5, §7 (stream), §4.5. Outgoing checks mean a stub or use-case bug can't ship an off-contract body. | Handlers returning plain objects: needs a second path for the stream. Next middleware/`proxy.ts` for CORS: a Next-only mechanism, and it would not be exercised by adapter tests. |
| D3 | **Body parsing reads bytes itself.** Rejects when `content-length` exceeds the cap, and also counts bytes while reading (chunked bodies have no header), cancelling the reader at the cap. Decodes with a fatal UTF-8 `TextDecoder`, then `JSON.parse`, then `schema.safeParse`. Every failure is a `RequestValidationError` → 422 `VALIDATION_FAILED`, with `z.prettifyError` as the message. `MAX_BODY_BYTES = 1 MiB`, private to `body.ts`. | WU-04 A8; §5 "422 = request body fails the contract". Next does not cap Route Handler bodies. | `request.json()`: unbounded. |
| D4 | **Oversized body → 422, not 413 (Q1).** §5 lists no 413 and `ErrorCode` has no fitting code. | Adding one is a contract change, which this unit excludes. | 413 + new `ErrorCode`: a contract change every backend must mirror, for a case no client handles differently. |
| D5 | **Content-type is not checked.** The body is parsed whatever the header says. | §5 defines failure by body content. No cookies or sessions exist, so a "simple" cross-origin POST gains nothing. Adding a check would be one more behaviour for every backend to mirror. | 415 / 422 on non-JSON content type. |
| D6 | **Error mapping.** `RequestValidationError` → 422 `VALIDATION_FAILED`. `LlmError` (code `LLM_REFUSAL` \| `LLM_UPSTREAM_ERROR`) → 502 with that code. Anything else, including non-`Error` throws → 500 `INTERNAL_ERROR` with a fixed generic message; the real error goes to `console.error`, never into the body. `LlmError` lives in `src/usecases/errors.ts`, so `src/llm` (WU-08) can throw it, use cases can see it, and `src/http` maps it without importing `src/llm`. | §5, §7, §9 dependency rule. | Defining it in `src/llm`: use cases couldn't reference it. Waiting for WU-08: scope needs 502 mapping now. This adds a class, not an `LlmClient` interface decision. |
| D7 | **CORS is static:** every response carries `Access-Control-Allow-Origin: <WEB_ORIGIN>`. Preflight answers 204 with `Allow-Methods: GET, POST, OPTIONS`, `Allow-Headers: content-type`, `Max-Age: 600`. | §5 names a single origin, and a constant header is trivial to port. | Reflecting a matching `Origin` + `Vary`: needed only for several origins. |
| D8 | **Every route must export `OPTIONS = preflight`, enforced by a test.** Next auto-answers `OPTIONS` without CORS headers if the export is missing, so a forgotten export breaks only browsers. An integration test globs `src/app/**/route.ts` and asserts each exports a working preflight, which covers routes added by WU-07–11. | ADR 0001 Q7. `/v1/trip/present` doesn't exist yet, so the adapter test uses `PresentRequest` with that URL, and the glob test guards the real route when it lands. | Relying on memory or a Note. |
| D9 | **Config.** `loadConfig(env)` is pure: Zod object → `Config`, or throws `ConfigError` listing *every* bad variable by name, never by value (it may hold the API key). `getConfig()` memoizes `loadConfig(process.env)`. Required: `LLM_MODE` (no default, so nothing silently picks a mode), `MODEL_FAST`, `MODEL_REASONING`, `MODEL_CRITIC`. `WEB_ORIGIN` defaults to `http://localhost:3000` (§5) and must be a bare origin (`new URL(x).origin === x`), because a trailing slash silently breaks CORS. `ANTHROPIC_API_KEY` is required for `live`/`record` only. | Unit scope; §5, §8.1, §8.3, §6.1. The config schema is not a wire schema, so `.refine`-style checks are fine here. | Defaulting `LLM_MODE`: hides misconfiguration. Hardcoded model defaults: forbidden by §8.1. |
| D10 | **Startup validation via `src/instrumentation.ts`:** `register()` calls `getConfig()`, and config is otherwise read lazily at request time, never at import, so `next build` needs no env. A functional test proves a bad env stops the server. If a throw in `register()` doesn't make `next start` exit non-zero, `register()` logs and calls `process.exit(1)`. | Unit scope "validated at startup". | Module-level `getConfig()` in routes: breaks or bakes in values during `next build`. |
| D11 | **Root `.env.local` is loaded by `next.config.mjs`** with Node's built-in `process.loadEnvFile()`, when the file exists (Q2). Node's loader doesn't override variables already set, so the harness's explicit env wins. | `.env.example` is at the root, but Next only reads env files from the app's own directory. No new dependency. | `@next/env`: an extra dep, and its module-level cache needs `forceReload`. A second `.env.local` under `backends/api-nextjs`: the same values in two places. |
| D12 | **`next.config.mjs`, not `.ts`.** `transpilePackages: ['@vp/domain-schema']`, `poweredByHeader: false`, explicit `turbopack.root` and `outputFileTracingRoot` at the repo root, `typescript.ignoreBuildErrors: true` (`pnpm typecheck` is the gate; no reason to run it twice). | §4.2. Next compiles `next.config.ts` to CJS, where `import.meta.dirname` is unreliable. Plain ESM avoids it. | `next.config.ts`. |
| D13 | **`tsconfig.json` is committed in the form `next build` wants,** so a build leaves no diff. It extends the base and adds Next's required fields, `next.config` plugin entry, `.next/types` and `tests` to `include`. T1 proves it: `git status` is clean after a build. `next-env.d.ts` stays ignored. | WU-04 note, test-layout note; §6.7 cleanliness. | Letting Next rewrite the file on each machine. |
| D14 | **Dedicated Vitest project `functional-api`** with `globalSetup` that runs `next build` once for that project. Its include is `backends/api-nextjs/tests/functional/**/*.test.ts`, and the existing `functional` project excludes that path. Root `test:functional` passes both `--project` flags explicitly. Each test file starts its own server from the one build via `startApi({ env })`, so later files (WU-09 upstream-failure) can use different env. | A global setup on the shared `functional` project would make the git-hook tests build Next too. Per-file builds would collide on `.next`. **Changes the WU-02 note's "functional project already collects it"; I'd record that as expected here, not a deviation.** | Building in the root script before Vitest: running Vitest alone would use a stale build. |
| D15 | **Harness process handling.** Spawns `process.execPath` with Next's bin JS (no shell, no `.cmd` shim), `--hostname 127.0.0.1` (no Windows firewall prompt), and a free port obtained by binding port 0. Env sets every config variable explicitly, plus `NODE_ENV=production` (Vitest sets `test`) and `NEXT_TELEMETRY_DISABLED=1`. Polls `/v1/health`, rejecting early with captured stderr if the child exits. Stop: `taskkill /pid <pid> /T /F` on Windows; `SIGTERM`, then `SIGKILL` after 5 s, on POSIX; it waits for the exit event. | Work-breakdown DoD; §3 Windows + POSIX; §6.1. Poll, not fixed sleep. | `pnpm start` via shell: killing the shim orphans the server on Windows. |
| D16 | **`GET /v1/health` is `force-dynamic`.** A functional test runs the built server with an unusual `WEB_ORIGIN` and asserts it comes back, which proves nothing was frozen at build time. | §5. | Trusting Next's default for GET handlers. |

## 6. Risks & open questions

**For you to decide (I'll proceed on the recommendation unless you say otherwise)**
- **Q1 — Oversized body status.** Recommend 422 `VALIDATION_FAILED` (D4): no contract change. The alternative is 413 with a new `ErrorCode`, which changes the contract.
- **Q2 — Root `.env.local`.** Recommend loading it from `next.config.mjs` (D11), so there is one env file at the root as `.env.example` implies.
- **Q3 — Unknown paths and wrong methods.** `/v1/nope` gets Next's HTML 404 and `POST /v1/health` an empty 405. §5 says "JSON only" but defines no 404/405 and `ErrorCode` has no fitting code. Recommend leaving it: a JSON version is a contract change. If you want it, it should be its own contract unit, because every backend would have to match.

**Risks**
- **R1 — `.ts` imports through `transpilePackages`** (WU-04 R1). T1 tests this first. If it fails, the fallback touches `domain-schema` imports and `gen`, which is a material deviation, so I'd stop and ask.
- **R2 — Next rewriting `tsconfig.json` on build.** Would show up as CI-only drift. D13 + T1 proof.
- **R3 — `register()` throw may not stop `next start`.** D10's fallback covers it; AC-API-17 proves the result.
- **R4 — Windows process and file locks.** Orphans holding the port or `.next`. D15 + AC-API-18. CI proves POSIX; Windows is proven only locally.
- **R5 — New Next release.** 16.4.5 is two days old (latest at planning time). pnpm's release-age setting or `pnpm audit --prod` may object. If so, I'd pick the newest version that passes and record it, without adding an audit exception.
- **R6 — Gate time.** `next build` adds to `pnpm verify` and the `pre-push` hook. Acceptable: it runs once per run (D14).
